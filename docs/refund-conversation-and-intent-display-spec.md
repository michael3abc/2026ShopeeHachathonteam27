# 退款對話與申請理解結果：UI 修改規格

日期：2026-09-12
用途：提供 fork 專案作為修改依據，描述目標與驗收方式，不限定框架、檔案位置或傳輸機制。

## 修改目標

讓使用者看得懂兩件事：**買家實際提出了什麼申請，以及系統把這份申請理解成什麼。**

本規格包含兩項改動：

1. 「使用者對話」以買家原始申請作為第一則訊息。
2. 「理解申請內容」的節點檢視呈現 LLM 的結構化理解結果。

兩者用途不同：對話保存買家說過的話；節點檢視呈現系統在該次執行得到的解析結果。解析結果不代表已符合退款資格或已核准退款。

## 一、使用者對話：從買家的原始申請開始

### 現況與問題

建立案件後，對話第一則訊息目前顯示類似「已送出訂單 XXX 的退貨退款申請」。這是系統確認訊息，無法讓買家回看自己當初輸入的商品問題與需求，也容易被誤認為買家原本說的話。

### 預期體驗

「使用者對話」是買家閱讀與補充案件的地方。第一則訊息應以買家身分呈現建立案件時實際輸入的申請內容，保留原文與必要換行，不用固定文案或 LLM 摘要代替。

例如買家輸入：

> 我收到的藍牙喇叭外殼有裂痕，外箱也壓壞了。我想只退這個喇叭並退款。

進入案件頁後，對話應先顯示上述買家訊息，再顯示系統回覆，例如「已收到申請，正在確認訂單與相關資料」。訂單編號可放在案件資訊區；若保留送出成功提示，應明確標示為系統訊息。

後續澄清、補件與買家回答沿用相同對話順序。若初始申請包含附件，應在原訊息旁提供適當的附件呈現，不把附件誤當成後來補交的內容。

### 粗略實作方向

- 建立案件時，同時保存初始申請為買家對話紀錄，保留角色、內容、時間及附件關聯。
- 案件頁讀取已保存的對話，以實際訊息呈現，不根據訂單編號組裝一則替代訊息。
- 即時顯示與重新載入使用一致的紀錄來源或訊息識別方式，避免同一則申請出現兩次。
- 舊案件若沒有保存原文，明確顯示「未保存初始申請內容」等狀態，不推測或重建買家原話。

### 驗收條件

- 建立案件後，第一則對話是買家實際輸入的原始申請，角色正確。
- 商品問題、申請範圍與希望的處理方式不會被固定送出提示取代。
- 系統確認訊息若存在，出現在買家申請之後，且不冒用買家角色。
- 重新整理或再次開啟案件，原始訊息仍存在，內容與順序一致，沒有重複。
- 後續澄清與補件正常接續；缺少歷史原文時不捏造內容。

## 二、節點檢視：呈現 LLM 對申請的理解

### 現況與問題

「理解申請內容」若只顯示模型呼叫完成、耗時或資訊完整度，使用者仍不知道系統究竟理解了什麼，也難以判斷為何接著要求澄清。

### 預期體驗

在「理解申請內容」的節點檢視加入「理解結果」，以清楚的欄位呈現該次解析：

| 欄位 | 顯示內容範例 |
| --- | --- |
| 申請原因 | 商品損壞、商品與描述不符 |
| 希望的處理 | 退款、退貨退款、換貨、尚未明確 |
| 申請商品 | 已辨識的商品名稱或商品編號；尚未確定則明示 |
| 資訊完整度 | 已足夠進入下一步、需要補充說明 |
| 待補充資訊 | 申請商品範圍、希望的處理方式；沒有則顯示「無」 |

以上是 LLM 已輸出的結構化解析結果，以可讀標籤呈現，不要求揭露模型內部推理，也不把解析結果當成退款決策。

同一節點可能執行多次，例如先解析申請、讀取訂單後再綁定商品，或收到澄清後重新解析。應讓每次執行保留自己的結果，方便比較理解如何更新，不把最新結果套到所有歷史紀錄。

### 粗略實作方向

- 重用理解申請步驟既有的結構化輸出，不為了顯示這些欄位再呼叫一次 LLM。
- 定義可供顯示的欄位集合，將原因分類、申請動作、商品參照、完整度與缺少資訊轉成前端可用的資料。
- 隨節點完成紀錄保存與傳送，關聯到對應案件及該次執行，支援重新載入與歷史回看。
- 前端將分類轉成易讀文字，保留「尚未辨識／尚未綁定／未記錄」等狀態，不猜測缺值。
- 商品名稱若有可信的訂單資料可對應，再顯示名稱；否則使用商品編號。缺少資訊只顯示核准的欄位分類，未知分類使用一般提示。
- 不直接輸出完整模型物件、原始 prompt、內部推理、個資或敏感附件連結。

### 驗收條件

- 點選已完成的理解節點，可看到該次解析出的申請原因、處理方式、商品範圍與完整度。
- 若資料不足，能看出還需要補充哪類資訊。
- 多次執行的結果各自對應正確，後來的結果不覆蓋早期理解。
- 重新整理後仍可看到已保存的結果；尚未完成或舊紀錄未保存時明確提示。
- 顯示功能不額外呼叫模型，也不改變澄清、補件、政策檢查、人工審核或退款授權流程。

## 三、簡要過程紀錄

1. 使用者在 demo 中希望了解各種案件經過哪些節點，進而提出要在理解節點中看到 LLM 解析內容。
2. 檢查後發現，既有節點檢視主要呈現呼叫紀錄與解說，理解結果沒有完整傳到畫面。
3. 本次工作環境已做出結構化理解結果的展示版本：擷取安全欄位、保存到節點摘要、依執行紀錄顯示。已驗證畫面與相關測試；fork 專案應依自身資料流導入，不必照搬檔名或契約名稱。
4. 試跑也發現，demo 訂單與政策資料有範圍限制。「查不到訂單」與「查不到適用政策」是不同終止原因，不能由「使用者要求退款」推導為一定能核准。理解結果展示可協助辨識申請原因，但不會補足缺少的政策。
5. 使用者接著提出：對話第一則應是買家輸入的原始退款申請，而不是系統生成的送出確認。此項已在 `feat/enhance-ui-feat` 以持久化 conversation API 呈現；移除固定買家替代訊息，保留換行與圖片。
6. 相關 UI 與契約測試通過，不代表所有真實模型路徑均已通過；完整 demo 曾在補件後仍被判定證據不足而終止，應與本規格的呈現驗收分開記錄。

## 範圍界線

本次聚焦原始對話與理解結果的可見性，不包含新增退款政策、擴充訂單資料、修改模型決策邏輯或保證所有申請自動退款，也不要求特定前端框架或訊息傳輸技術。

## 功能分支實作邊界（2026-09-12）

- 圖片支援選取、拖曳、貼上、逐檔重試／移除與刷新還原；初次申請及補件沿用附件引用，實際檔案由 API 保存。
- 理解結果以共享 `IntentDisplay` 放入可選 `NodeSummary.intent_display`，只含原因分類、申請動作、商品識別碼、完整度及允許的待補充分類；未知分類顯示一般提示，不傳模型自由文字。
- `parse_request` 與 `load_case_context` 各自保存當次結果；前端按 run／attempt／operation 關聯並去重。讀取訂單後的商品綁定不覆寫早期解析。首版只顯示商品識別碼。
- 舊 Activity 缺少展示欄位時提示未記錄；對話分別提示載入中、讀取失敗及無歷史內容。不重建舊案件原話，不新增資料表或 LLM 呼叫。
- Terra medium 真實 Resolver smoke：8.619 秒辨識 synthetic 喇叭右下角裂痕並要求到貨證據，停在補件；使用約 258 KB JPEG。gateway 預設 1 MiB request 上限仍小於 UI 圖片上限，大圖及完整 Reviewer／退款模型流程尚未驗收。
- 本次採最小收尾；新增理解結果的完整桌面／手機及延遲事件瀏覽器專項驗收未完成，與既有圖片瀏覽器測試區分。
